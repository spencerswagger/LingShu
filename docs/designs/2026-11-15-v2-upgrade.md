## 1 存量数据映射

### 1.1 三条总则

1. **配置本体不迁**：渠道、协议、密钥、限流、探活、优先级在 V2 里由外部网关唯一持有；灵枢只保留「对外模型 ↔ 内部模型」绑定与账号财务扩展（数据层契约 §2.1–§2.4）。把老配置搬进新表必然造出第二份真源。
2. **只有三个字段能落位**（渠道名、密钥名、内部模型名），且**都只能作为候选值**：网关侧的 provider/账号命名空间与老库的渠道名/密钥名不是同一套字符串，字符串相等不代表同一实体。
3. **不可再生数据不迁移、单独留档**：凭据密文（SM4 密文与网关存储格式/主密钥不通用）、`cost_rates`（V2 没有"自配成本倍率"这一层）、订阅账期（老库没有这张表）。丢弃必须留归档 dump + 清单，不允许静默。

### 1.3 处置清单（映射不了的数据）

> 「行数量级」按表性质给上界（配置表 O(10¹–10²)，日志表 O(10⁵–10⁷)）。**生产真值必须在上线前用体检脚本取**（§1.4 P2），本文不填猜测数字。

| # | 数据 | 处置 | 理由 | 影响面 |
|---|---|---|---|---|
| C1 | `channels.base_url` / `protocol` / `channel_protocol_id` | **丢弃**（0024 DROP 表）；在网关重建，重建清单 = 渠道 × 协议 | 灵枢不再持有上游接入配置 | 行数 O(10¹–10²)；无对外接口。漏建 → 该供应商请求 5xx，由网关兜底 |
| C2 | `channels.tags` + `channel_tags` + `semantic_tags` + `tokens.tag_id` | **丢弃 + 归档** | 标签只服务 V1「按标签选渠道」；V2 无路由。`tokens.tag_id` 在 0024 被删列 | `channel_tags` O(10²)；`tokens.tag_id` 非空行数 = 绑过标签的令牌数。**行为变化**：同一外部模型对所有令牌同价同路，标签差异化分流消失（不报错） |
| C3 | `channels` / `channel_models` 的 `rate_limit`、`health_probe`、`reliability` | **丢弃** | 限流与探活归网关 | 若运营真在用这些限额参数，需人工抄到网关；漏抄 → 限额失效（**只丢保护，不丢账单**） |
| C4 | `channel_keys.credential_enc`（全部密钥密文） | **丢弃 + 归档**；在网关侧**重新录入** | SM4 密文与网关存储不通用；凭据不得进灵枢库 | 行数 = 密钥数 O(10¹–10²)。**最大的人工工作量与最大风险**：漏录一把 key **不报错**，只是该账号不可用 → 组内改道/降并发，账面上表现为"某供应商流量归零" |
| C5 | `channel_models.cost_rates`（成本倍率） | **丢弃 + 归档**；历史成本留在 `billing_records.cost_credits` | V2 成本只有账本实付与订阅摊销两种来源 | 行数 O(10²–10³)。**口径跳变**：盈亏页切换前后成本不是同一算法 → 新旧数据不能同图（§4.3） |
| C6 | `probe_logs`（探活历史） | **丢弃 + 归档** | 探活归网关；V2 无探测 | 行数 O(10⁴–10⁶)（最高频日志表）。仅丢历史可查性（V1 渠道详情页在 V2 已整体重写） |
| C7 | `auto_models` / `auto_model_members`（auto 名） | **逐条判定，默认丢弃**。判定：`enabled=true` 且近 30 天 `billing_records.auto_model_name` 有命中 → **人工转为对外模型**（取 `position` 最小成员承载该名）；其余丢弃 | auto 名是对外可调用名，丢掉就是客户端 404；但 V2 拓扑没有 auto 位置 | 用 `billing_records.auto_model_name`（0011 加的列）可直接数出近 30 天命中量，**必须按清单逐条处理** |
| C8 | `subscriptions` 账期/月费（新表，老库无源） | **人工补录**（每账号 1 行） | 月费是财务事实，不可推导 | 行数 = 订阅类账号数。未补录 → `share_cost` 无数据、摊销成本恒 0、**毛利虚高且无任何告警** |
| C9 | 拓扑坐标（`model_links`） | 无历史，**默认自动布局** | V1 无画布 | 仅影响拓扑页首屏观感 |

归档（0024 之前一次性）：

```bash

pg_dump -Fc -Z6 -t channels -t channel_keys -t channel_models -t probe_logs \
        -t auto_models -t auto_model_members -t semantic_tags -t channel_tags \
```

## 2 升级顺序与停机

### 2.1 两条路径与执行序

先定三条事实，它们决定下面的一切：

- `db.Migrate` 按**文件名字典序**依次应用，每文件一个事务、失败回滚（`internal/db/migrate.go:40`、`:70`、`:74`）。「0024 排最后」不是人为顺序，而是编号决定的事实。
- 服务启动先迁移再对外服务（`cmd/server/main.go:144`），迁移失败 `os.Exit(1)`（`:146`）——不存在"带病启动"。
- 存在 `-migrate-only`（`cmd/server/main.go:110`、`:149`），可以只跑迁移不起服务。

| 路径 | 形态 | 客户端停机 | 前提 |
|---|---|---|---|
| **A（零停机，推荐）** | 两次发布 + 双栈并行：V2-a（含 0019–0023）→ 灰度 → V2-b（含 0024） | **无**（只有亚秒锁抖动） | §2.3 四条全满足 |
| **B（单窗切换）** | 一次整链 0019→0024 + 停旧起新 | 2.5 分钟量级（§2.4） | 无（但老栈此后再无回退可能） |

#### 0019 → 0024 每步做什么

| 文件 | 做什么 | 动的对象 | 可回退 | 在路径 A 的哪一步执行 |
|---|---|---|---|---|
| 0019 `v2_topology` | 建 `internal_models` / `model_links` / `subscriptions` 三表 + `external_models.bound_internal_ref` 加列与部分索引 | 3 张新表 + `external_models` 增 1 列 | 是（结构）／丢订阅数据（§3.1） | A4 |
| 0020 `v2_billing_attribution` | `billing_records` 纯加 7 列（`request_id`、`upstream_*` 四列、`ledger_entry_id`、`cost_source`）+ 3 个 CHECK + 3 个部分索引，零 DML | `billing_records` | 是（结构）／丢归因数据（§3.1） | A3 预建列与索引 → A4 补约束 |
| 0022 `v2_ledger` | 建 `ledger_entries`（九字段 + 幂等键）与 `credit_holds`（阶段一空壳） | 2 张新表 | 是 | A4 |
| 0023 `v2_reconcile` | 建 `reconcile_windows`（60 s 窗、四计数列、`status` 五值、`alarm_streak`、`fetch_offset`） | 1 张新表 | 是 | A4 |
| 0024 `v2_drop_legacy` | 先删 3 个阻塞列（`billing_records.channel_key_id`、`sessions.channel_key_id`、`tokens.tag_id`），再删 11 条 `DROP TABLE`（实删 10 张，`channel_events` 已在 `0009` 删除） | 退役表与阻塞列 | **否** | A10（灰度满 7 天后） |

#### 路径 A 的执行序（V2-a / V2-b 两个构建）

|---|---|---|---|---|

| A4 | **V2-a 跑 0019–0023**（不含 0024）：`server -migrate-only` | V2-a 二进制 | 亚秒锁抖动 | 手写反向 SQL（§3.1，此时无数据损失） |
| A5 | 复核：保留表行数不变少（契约 §5 步骤 3c） | `psql` | 无 | — |

| A8 | 入口按令牌白名单 5% → 50% → 100%（§5.2） | 入口 | 无 | 白名单切回老栈（秒级） |
| A9 | 100% 后连续观察 **7 天**，判据 A/B（§3.4）满足 | 监控 | 无 | 同上 |
| A10 | **V2-b 跑 0024**（此时老栈已不接单）：`server -migrate-only` | V2-b 二进制 | 亚秒锁抖动（仅剩 `billing_records` 等表的短暂排他） | **不可退**（§3.2） |

**发布要求（路径 A 成立的必要条件）**：V2-a 构建的迁移目录里**不能包含 `0024`**——`migrate.go` 会把未应用的文件一次全跑，靠"人记得别跑 0024"是无效控制。这也是「库先行动、0024 排最后」在工程上的确切含义：**0024 独立成一个补丁发布**。

#### 路径 B 的执行序（单窗，不拆发布）

| 步 | 动作 | 客户端影响 |
|---|---|---|
| B0–B2 | 同 A0–A2（体检 / 备份 / 基线） | 无 |
| B3 | 停老进程（停止接单） | **开始停机** |
| B4 | 一次整链 `0019 → 0020 → 0022 → 0023 → 0024`（新二进制 `-migrate-only`） | 停机中 |
| B5 | 复核 3c/3d 断言；`sys_configs` 派生（A6） | 停机中 |
| B6 | 起新进程 + 健康检查；放开流量 | **结束停机** |

B 路径没有灰度能力（V1 转发链已从新版本删除，见 §2.3 依据 1），也就不存在"5% → 50% → 100%"；如果决策选 B，§5 的灰度方案作废，只剩"100% 切换 + 7 天观察"。

### 2.2 迁移器的四条行为事实

| # | 事实 | 出处 | 升级含义 |
|---|---|---|---|
| M1 | 按文件名字典序应用，每文件一事务 | `migrate.go:40`、`:70` | 编号即执行序；单文件失败整体回滚，不留半截 |
| M2 | **无并发互斥**（全仓无 advisory lock） | `grep -n advisory` 无命中 | **禁止两个实例同时跑迁移**：后到者撞 `INSERT INTO applied_migrations` 主键冲突并退出。部署必须"单实例先跑迁移，再起其余副本" |
| M3 | 迁移语句在事务内执行 | `migrate.go:70-81` | **`CREATE INDEX CONCURRENTLY` 写不进迁移文件**（不能在事务块内）→ 想躲建索引长锁只能预建（§2.5） |
| M4 | 只有 up、没有 down | `migrations/` 无 `*down*`；`migrate.go` 只有 apply 分支 | 「回滚」= 手写反向 SQL（§3.1） |

### 2.3 能否零停机：**能，但只有路径 A，且四条前置缺一不可**

| # | 前置 | 依据 | 缺了会怎样 |
|---|---|---|---|
| Z1 | 0019–0023 全部是**纯增**语句（无 DROP、无 DML） | 数据层契约 §1 / §3；且老代码全仓**无 `SELECT *`**（`grep -rn "SELECT \*" internal` 为空）→ 新增列/新表对老栈完全无感 | 老栈与新栈就能共库；只要有一条 DROP，双栈立刻破 |
| Z2 | 建索引改成**预建 `CONCURRENTLY`**（§2.5） | M3 + 0020 三个索引是唯一随行数增长的语句（§2.4） | 迁移期间 `SHARE` 锁阻塞写入 2–80 s → 请求堆积，等于短暂停机 |
| Z3 | 新版本灰度期**不写 `sessions`** | `sessions.channel_key_id` 是 `NOT NULL REFERENCES channel_keys(id)`（`0001_init.sql:230`）；新代码没有渠道密钥概念，只能写 `NULL` → 约束拒绝 | 新栈写会话必失败；若强行写，就要改 0019 契约加 `DROP NOT NULL`（§7-2） |
| Z4 | 入口能按**令牌明文精确匹配**分流 | 灵枢令牌不带租户前缀，无法按前缀/用户段路由 | 无法分批放量，只能一次切（= 路径 B） |

四条都满足时：客户端全程无感——老栈持续服务，新栈只吃白名单，DDL 只在 `ADD COLUMN` / `ADD CONSTRAINT NOT VALID` / `DROP` 这类元数据操作上产生**亚秒排他锁**（毫秒级），配合"迁移前清理长事务"即可（§2.5 末尾）。

### 2.4 单窗切换（路径 B）的最短停机窗口估算

窗口 = `停接单(2 s) + 迁移 + 复核(1 s) + 配置派生(1 s) + 启停与健康检查(5–15 s) + 观察(10 s)` ≈ **固定开销 20–30 s + 迁移耗时**。

迁移耗时逐语句拆解（关键判断：**只有一组语句随行数增长**）：

| 语句组 | 文件 | 锁 | 随行数增长 | 依据 | 1M 行 | 20M 行 |
|---|---|---|---|---|---|---|
| `CREATE TABLE` ×3 + 索引 | 0019 | 无（新表） | 否 | 空表建表 | <0.3 s | <0.3 s |
| `ADD COLUMN IF NOT EXISTS`（含 `bound_internal_ref`） | 0019 / 0020 | 表级排他 | 否 | PG 11+ 加"无默认值"列只改目录、不重写表 | <0.1 s | <0.1 s |
| `ADD CONSTRAINT … CHECK … NOT VALID` ×3 | 0020 | 表级排他 | 否 | `NOT VALID` 跳过存量行扫描 | <0.1 s | <0.1 s |
| **`CREATE INDEX` ×3（均带部分谓词）** | 0020 | **`SHARE`（阻塞写、允许读）** | **是** | 非并发建索引必须整堆扫描；历史行在三个谓词上全为 `NULL` → 索引条目为 0，但扫描免不掉 | 2–4 s | 40–80 s |
| `CREATE TABLE` ×3 + 索引 | 0022 / 0023 | 无（新表） | 否 | 空表 | <0.4 s | <0.4 s |
| `DROP COLUMN` ×3 + 11 条 `DROP TABLE` | 0024 | 逐表排他（须等锁释放） | 否 | DROP 只改目录 + 提交时 unlink 文件，与表大小无关 | <0.5 s | <0.5 s |

扫描口径：`billing_records` 行宽约 0.4–0.6 KB（`tokens`/`rates`/`coefficients` 三个 JSONB 撑着）→ 1M 行 ≈ 0.4–0.6 GB；本地 SSD 顺序扫描 100–300 MB/s → **1.5–4 s / 百万行**（取整 2–4 s）。

| `billing_records` 行数 | 未预建索引（路径 B 常规） | 预建索引（路径 A / 预建后的 B） | 建议预算 |
|---|---|---|---|
| ≤ 1M | ≤ 35 s | ≤ 30 s | 5 分钟 |
| ≈ 5M | ≤ 55 s | ≤ 30 s | 5 分钟 |
| ≈ 20M | ≤ 130 s | ≤ 30 s | 5 分钟 |
| > 20M | 按 4 s/百万行线性外推 | ≤ 30 s | 10 分钟，且**必须**预建 |

**结论：按 5 分钟给停机预算，覆盖到 2000 万行账单**；超 2000 万行必须预建索引，否则窗口不可控。表内 ±2 倍误差由 §6 演练实测校正——演练的唯一目的就是把这两列从估算换成实测。

### 2.5 把行数依赖消掉的唯一手段：预建索引

```sql
-- A3 做（服务照常接单；CONCURRENTLY 不阻塞读写）
-- 前提：索引涉及的 4 列已存在 → 先 ADD COLUMN（同为毫秒级元数据操作），或等 0019/0020 跑完再建
ALTER TABLE billing_records ADD COLUMN IF NOT EXISTS ledger_entry_id   TEXT;
ALTER TABLE billing_records ADD COLUMN IF NOT EXISTS upstream_provider TEXT;
ALTER TABLE billing_records ADD COLUMN IF NOT EXISTS upstream_account  TEXT;
ALTER TABLE billing_records ADD COLUMN IF NOT EXISTS request_id        TEXT;

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS uq_billing_ledger_entry
  ON billing_records(ledger_entry_id) WHERE ledger_entry_id IS NOT NULL;
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_billing_upstream_time
  ON billing_records(upstream_provider, upstream_account, call_time DESC)
  WHERE upstream_provider IS NOT NULL;
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_billing_request
  ON billing_records(request_id) WHERE request_id IS NOT NULL;
```

预建后，迁移文件里的同名 `CREATE INDEX IF NOT EXISTS` 变成空操作 → 迁移耗时与行数脱钩。
`CONCURRENTLY` 建索引失败会留下 `INVALID` 索引：必须校验（`SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;` 应为空），失败则 `DROP INDEX` 后重跑。

迁移前必做（防锁等待放大成停机）：确认无长事务与长报表任务占着表——`SELECT pid, state, xact_start, query FROM pg_stat_activity WHERE state LIKE 'idle in transaction%' OR (now()-xact_start) > interval '1 minute';`。需要硬保护时在 DSN 上加 `options=-c lock_timeout=3s`（DDL 抢不到锁就快速失败重试），**不要**为此改迁移文件。

## 3 回滚

### 3.1 0019–0023 的 down 路径逐条判定

前提（M4）：**仓里没有 down 机制**——无 `*_down.sql`、无回滚命令。下表「可用」= 手写反向 SQL 能否让库回到上一版结构，以及数据是否还在。

| 文件 | 反向 SQL | 结构可逆 | 数据可逆 | 会丢什么 | 判定 |
|---|---|---|---|---|---|
| 0019 `v2_topology` | `DROP TABLE internal_models, model_links, subscriptions`；`ALTER TABLE external_models DROP COLUMN bound_internal_ref` | 是 | **否** | `subscriptions` 全部财务录入（月费/账期/币种/分摊开关）——**无上游可重放，纯人工数据**；`model_links` 坐标；`internal_models` 可重同步（不心疼） | **有条件可用**：`subscriptions` 有数据后回退 = 删财务台账 |
| 0020 `v2_billing_attribution` | `DROP INDEX`×3、`DROP CONSTRAINT`×3、`DROP COLUMN`×7 | 是 | **否** | 已写入的 `request_id` / `upstream_*` 四列 / `ledger_entry_id` / `cost_source`：归因与账本关联**永久丢失**，事后只能从网关日志重推且不保证对得上 | **有条件可用**：有新流量写入后回退即丢这段归因 |
| 0022 `v2_ledger` | `DROP TABLE ledger_entries, credit_holds` | 是 | 是（有条件） | `ledger_entries` 是网关账本镜像，可重拉——**前提是网关保留历史账本**（未证实，§7-8）；`credit_holds` 阶段一未启用，零损失 | **可用**（唯一真正无损的一条） |
| 0023 `v2_reconcile` | `DROP TABLE reconcile_windows` | 是 | 是（有条件） | 只有对账结论；窗口可由 `billing_records` + 账本重算 | **可用** |
| 0024 `v2_drop_legacy` | **无** | **否** | **否** | 11 条 DROP 语句（实删 10 张表——`channel_events` 早在 `0009` 已删）+ 3 个阻塞列 | **不可用**（§3.2） |

一句话：**结构都能退，数据只有 0022/0023 能退**。0019 与 0020 的回退要按"数据删除"审批，不是一个 DDL 操作。

### 3.2 0024 之后：只剩「从备份恢复」

1. **反向 DDL 恢复不了内容**：重建 `channels (…)` 得到空表，老数据只在归档 dump 与全库 dump 里。
2. **应用层同时失效**：0024 删的三列是老代码硬依赖——`billing/query.go:43` 用它过滤、`billing/stats.go:340-341` `JOIN channel_keys/channels`、`console/cost.go:143-146` 与 `:600-601` 同款 JOIN、`console/admin.go:311/351/372` 直查这两张表、`identity/token.go:56` 的 `tokenCols` 含 `tag_id`。跑老版本必须"恢复库 + 回退二进制"同时做。
3. **只能回到备份时刻**：恢复会丢掉 0024 之后写入的 `billing_records` / `credit_flows` / `ledger_entries`。**回滚 = 真实账单丢失**，必须走事故单。

因此 0024 只在**路径 A 的 A9 判据通过后**执行；路径 B 则是"切换即接受不可回退"。

### 3.3 从备份恢复的耗时量级

口径：`pg_restore -j4`，本地 SSD，dump 由 `pg_dump -Fc -Z6` 产生；dump 体积 ≈ 0.3–0.6 KB/账单行。

| 数据规模 | dump 体积 | 还原耗时 | 含校验总计 |
|---|---|---|---|
| 1M 行 | 0.3–0.6 GB | 60–180 s | ≈ 3–5 分钟 |
| 5M 行 | 1.5–3 GB | 3–8 分钟 | ≈ 8–10 分钟 |
| 20M 行 | 6–12 GB | 10–25 分钟 | ≈ 25–30 分钟 |

判据式：**≈ 1–2 分钟 / GB + 一次全表行数比对**。0024 之后的回滚是"半小时级事故"，不是"分钟级操作"——这是把它排最后、并用 7 天观察期兜住的理由。

### 3.4 老版本应用保留多久（判据，不按天数拍）

| 判据 | 阈值 | 为什么是这条 |
|---|---|---|
| A 线上稳定 | 100% 切换后连续 **7 天**无 P0/P1，且每日对账 `alarm_streak` 全程为 0 | 对账是唯一能自动发现"漏账"的机制（数据层契约 §7），它静默通过才算真稳 |
| B 账务守恒 | 连续 7 天每日余额守恒校验通过（§5.3 指标 4） | 计费面的错都是静默的，必须靠守恒兜 |
| C 备份可信 | 归档 dump + 全库 dump 各做过一次**脱机还原 + 行数比对**，产物留 sha256 | 没验证过的备份不算备份（契约 §5 判定点 B） |

保留策略：

- **可回退期**（0024 未执行，即路径 A 的 A8–A9）：老二进制与老栈必须常备，**5 分钟内可切回**。这是灰度期唯一的安全网。
- **0024 执行后**：老二进制降级为"读归档数据 / 复现问题"用途，保留 **90 天**（与备份保留期一致），不再打补丁；老分支以 git tag 永久保留（零成本）。

## 5 灰度

### 5.1 灰度的物理前提（两条硬约束 → 只能是双栈）

| # | 约束 | 依据 | 后果 |
|---|---|---|---|
| G1 | 单进程内没有 V1 转发路径 | 数据层契约 §9.2（路由/互译整段删除） | 不能"同进程按百分比切流" |
| G2 | `sessions.channel_key_id` 是 `NOT NULL REFERENCES channel_keys(id)` | `0001_init.sql:230` | 0024 之前新代码**无法写会话行**（只能写 `NULL`） |

结论：**灰度 = 双栈并行（老栈 + 新栈共库）+ 入口按令牌白名单分流**，并行期必须落在「0019–0023 已应用、0024 未执行」区间（否则老栈被删列打死）。G2 只在「新版本灰度期不写 `sessions`」时不成阻断——这是必须拍板的前提（§7-2）。

入口分流要求：按**令牌明文精确匹配**（如入口层 `map $http_authorization` 白名单）。按随机百分比分流不可接受：同一会话、同一对账窗口会横跨两条链路，归因与差额无法定位到链路。

### 5.2 三阶段放量

| 阶段 | 放量口径（按上周 `billing_records` 的令牌维度请求量排序累计） | 前置 | 最短观察 | 晋级条件 | 回退动作 |
|---|---|---|---|---|---|
| **5%** | 白名单 = 累计占比 ≈5% 的令牌（≤5 个，必须含 1 个自有测试令牌） | A0–A7 完成、0024 **未**执行、P1–P5 全绿 | 24 h | 四条指标全绿 ≥24 h（§5.3） | 入口白名单切回老栈（秒级，无数据动作） |
| **50%** | 白名单扩大到累计 ≈50% | 5% 阶段晋级条件满足 | 48 h | 四条指标全绿 ≥48 h，且 `reconcile_windows` 全程 `alarm_streak = 0` | 同上 |
| **100%** | 全量入口切新栈，老栈停止接单（保留可启动状态） | 50% 阶段晋级条件满足 | **7 天** | 7 天全绿 + 判据 A/B（§3.4）满足 → 才允许执行 **0024** | 0024 前：入口切回老栈；0024 后：§3.3 备份恢复 |

关键点：**100% ≠ 不可逆**。100% 之后 7 天内老栈仍可拉起（库里只多了表和列，没删），0024 才是不可逆点。这是"0024 排最后"在运维上的唯一价值。

### 5.3 观察指标与回退阈值（每个都给数值与判定窗口）

| # | 指标 | 定义 / 采集 | 回退阈值 | 判定窗口 | 动作 |
|---|---|---|---|---|---|
| 1 | **错误率** | 新栈 `billing_records` 中 `status='failed'` 占比与进程 5xx 计数，两口径取大 | 滚动 **10 分钟** > **0.5%**；或连续 **3 个 1 分钟**点 > **2%** | 每 1 分钟采一次 | 立即回退（切入口） |
| | 基线 | 灰度前 24 h 同口径；若基线本身 >0.5%，阈值改 **基线 + 0.3 个百分点** | — | — | — |
| 2 | **对账差额** | `reconcile_windows` 的 `local_tokens` vs `upstream_tokens`；判定与对账作业同口径：窗口整体 token 相对偏差 > **2%** 且 `upstream_tokens ≥ 10000` 记 `alarm`；分组（key × 模型）偏差 > **5%** 且组内笔数 ≥5 记明细 | 连续 **3 窗** `alarm`（`alarm_streak ≥ 3`）→ 回退；单窗偏差 > **10%** → 立即回退 | 60 s/窗，连续 3 窗 | 回退 + 冻结该供应商账本拉取 |
| | 笔数差 | `local_count` vs `upstream_count` 不等 | **不单独触发回退**（失败/拒绝请求在账本侧天然缺席），只进 `detail` 人工判读 | — | — |
| 3 | **P99 延迟** | `billing_records.duration_ms` / `first_token_ms` 分位值（列已存在，无需新埋点） | P99 总时长 > 灰度前 **7 天同时段** P99 × **1.3**；或 `first_token_ms` P99 > **5000 ms**（首包硬超时是 30000 ms，拿它当阈值等于"已经超时了才告警"） | 连续 **3 个 5 分钟**窗 | 回退；先查 `upstream.base_url` 与流空闲超时配置 |
| 4 | **余额一致性** | 每 5 分钟比对 `Σ credit_flows.amount` 与 `Σ Δcredit_wallets.balance` | 绝对差 > **0.01 积分**（`NUMERIC(20,5)` 的最小可见单位），或出现"余额 < 0" | 1 小时内出现 **2 次** | 回退 + 人工对账；出现 `type='set'`（绝对值覆盖）则**重置基线**，不计入差值 |
| 5 | **账本新鲜度**（辅助） | `max(ledger_entries.occurred_at)` 落后 `now()` 的秒数 | > **180 s** 告警（连续 3 窗）；> **15 分钟**按"对账不可用"处理（窗口记 `skipped`） | 每轮 | 不回退，但**禁止晋级** |

硬规矩（防"观察是否异常"式放量）：

- 任一指标**当前不可得**（采集失败/无数据），该阶段**不得晋级**。
- 5% 与 50% 阶段的回退**不涉及任何数据动作**（只切入口），必须 5 分钟内完成；这是灰度能与 0024 解耦的前提。
- 阈值调整必须同步改本文与对账作业配置，禁止口头放宽。
