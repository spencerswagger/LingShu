# 请求失败综合整治（Request Error Remediation）

> Status: DRAFT (rev1 — 待用户审批；审批通过后拆分为各 Phase 的子设计 → 计划)
> Author: agent
> Last updated: 2026-10-18
> 调查方式：按 S1–S7 分派子代理逐项排查代码库现状（路由/状态机/协议/别名/流式），结论已并入本文。

## Intent Contract

```
intent: 把「请求失败」从硬编码、不可区分的处理，演进为「以渠道协议为扩展点的可配置错误处置 + 协议特性 + 可运维决策轨迹」，消除请求/协议侧错误对渠道健康度的误伤，并为后续供应商/模型的协议差异提供低成本兼容路径。
constraints:
  - 不改变计费公式与系数、路由选择算法、会话亲和粒度与既有 failover 语义（除管理员显式配置的错误处置）。
  - 向后兼容：未配置任何策略/特性时，行为与改造前逐字节一致（默认安全态）。
  - 协议错误策略与协议特性只影响其挂载的协议/渠道；全局默认保持安全态（策略/特性逐项启用）。
  - 上游错误「可控化」不在范围内——我们只做分类、计数与处置，不承诺修复上游。
  - 迁移单向新增，不改既有列语义。
  - 单实例内存模型（不引入多实例一致性/Redis 广播）。
  - go build / go vet / go test ./... 必须绿；并发相关 go test -race 零告警。
success_criteria:
  - 可在渠道协议上为每个「错误签名」配置处置（计入健康错误率 / 不计入 / 是否 failover / 触发动作 none-drain-disable / 下游状态码映射），且协议级错误按类型计数可查。
  - 内置协议特性可使：DeepSeek thinking 模式请求不再因未回传 reasoning_content 而 400；web_search 类工具请求不再因 input_schema 缺失而 422。
  - 决策轨迹包含「排空(DRAIN)」排除原因（可直接映射运维动作：状态/探测、会话、限流）。
  - 每个失败请求的可运维轨迹完整：候选为何被排除、流式失败区分「已送达/未送达」、含响应阶段诊断。
  - 对外模型可配置多个别名，工具默认模型名可直接命中。
risk_level: high   # 触及渠道健康熔断（误判可致全渠道排空）与请求/响应协议改写路径
```

## Verification Contract

```
verify_steps:
  - run tests: cd backend && go test ./...
  - race: cd backend && go test -race ./internal/domain/channel/... ./internal/domain/gateway/...
  - build: cd backend && go build ./... && go vet ./... ; cd frontend && npm run build
  - check:
      1) 错误策略表驱动：对每种错误签名（422 工具 schema / 404 路径 / 400 reasoning / 5xx / 超时 / 429 / 401）各一例，断言
         「是否计入健康」「是否 failover」「触发动作」「下游状态码」与配置一致，并断言状态机（FeedResult）实际未被误喂。
      2) 协议级错误计数：各错误类型计数增量正确，且互不串台（按协议 × 类型）。
      3) 协议特性：thinking 回传特性开启后，请求体正确携带 reasoning_content（多轮）；未开启时请求体与改造前一致。

      5) 决策轨迹：构造「仅因排空而无候选」场景，断言轨迹中出现排空项；流式失败断言区分已送达/未送达且含响应阶段诊断字段。
      6) 默认安全态回归：未配置策略/特性时，路由结果、错误码、请求体、错误率 与改造前一致。
  - confirm:
      1) 配置「422 不计入健康」后，持续 422 不再抬升错误率、不触发排空。
      2) 配置「某 5xx 计入健康且 failover」后，行为与预期一致。
      3) 开启 thinking 特性后 DeepSeek thinking 请求成功率恢复；关闭后回退原行为。
      4) 关闭所有开关后行为与改造前逐字节一致。
```

## Problem（问题）

pre-release 已运行一段时间，积累的请求错误按数量降序为 S1–S7。现状定位与根因如下（结论来自代码库排查，非推测）：

| 编号 | 现象 | 现状定位（模块级） | 根因 / 缺口 |
|---|---|---|---|
| **S1** | 无可用渠道 | 网关已有候选级决策轨迹（候选 `attempts` → 调用日志 `decision` 轨迹 + 结构化 `attempt_trail`）；终态分流为 400（协议不支持）/ 429（限流）/ 503（其余） | ①轨迹**唯缺「排空(DRAIN)」排除原因**（排空在路由层即被静默剔出新会话候选，不进轨迹）；②排空/禁用/会话满/限流这些原因虽已记录，但**未与运维动作显式对齐**；③错误率超限的根因是「**未区分何种错误**」（见交叉根因） |
| **S2** | 上游流式请求失败（已送达，不转移） | 流式转发入口，`已送达=true` 且 `Do` 失败（多为响应超时）分支：落失败账单 + 调用日志 + 502 | 结构化日志 `kind` **两种情况都记为 `connect_failed`**，不区分「已送达」；缺响应阶段诊断（是否收到首字节、阶段耗时等），难以定位 |
| **S3** | 模型 xxx 未配置或已停用 | 模型解析只命中「启用且未软删」的精确 `external_name`；现存唯一「别名」能力是 Auto 模型（有序成员组），**不支持一模型多别名** | 工具（claude code 等）在工具/subagent 调用时指定其内置默认模型名，用户未覆写 → 无同名外部模型直接 404 |
| **S4** | 上游 422（web_search 缺 input_schema） | 全仓**零 422 专门处理** → 落通用失败分支：**计入渠道错误率** + 不 failover → 502 | 属**请求/客户端归因**（工具 schema 问题），却被当作渠道健康失败 → 误排空健康渠道 |
| **S5** | 上游 404 | 404 被纳入**可 failover**，但仍回喂通用失败（**计入错误率**） | 多为上游路径/模型配置问题，被误计入渠道错误率 → 误排空 |
| **S6** | 上游 400 reasoning_content thinking 必须回传 | 仅做了**响应侧** reasoning_content 采集/计费；**请求侧思考模式适配完全缺失**；400 不可 failover → 502 **且计入错误率** | 上游（DeepSeek 等）要求多轮把 reasoning_content 回传，本地未做请求侧回传 → 必失败且反复抬升错误率 → 几乎不可恢复 |
| **S7** | 上游流式连接失败 | 流式转发入口，`已送达=false` 分支：**可安全 failover** | 信息相对完整，主要是与 S2 的观测区分度不足 |

**交叉根因（贯穿 S1/S4/S5/S6）**：渠道状态机只识别 成功 / 429 / 401-403 / 超时 四类，`400 / 404 / 422 / 5xx / 网络` 全部塞进同一个 **generic failure 桶**共同推高错误率。于是任何**请求/协议归因**的错误都会污染渠道健康度并触发排空——这正是「没有正确区分何种错误」的直接后果。

## Vision（目标愿景）

1. **错误处置从硬编码走向可配置**：以**渠道协议**为扩展点，管理员可为每个错误签名设定处置（计入健康 / 不计入 / 是否转移 / 是否禁用·排空 / 下游状态码）。上游错误不可控且形态繁多，配置化比逐案改代码更可持续。
2. **协议差异以「特性」低成本兼容**：以**渠道协议的代码特性**承载供应商/模型差异（如 thinking 回传、工具 schema 归一），新增特性只加代码注册，不改主链路。
3. **每次失败都可运维**：候选决策轨迹补全且与运维动作对齐；协议级错误按类型计数；流式失败可区分阶段。
4. **为动态感知打基础**：协议级错误统计沉淀为历史数据，作为后续 RPM/TPM 动态感知的数据基础（本期不做学习）。

## Non-goals（不做）

- 会话优化（已在其他设计中推进，本期明确排除）。
- 动态限流感知（RPM/TPM 由历史数据猜测）——本期只沉淀统计，不做学习算法。
- 多实例一致性 / Redis 失效广播（沿用单实例内存模型）。
- 计费公式与系数、路由算法、会话亲和与既有 failover 语义的变更。
- 上游错误「可控化」（我们只分类、计数、按策略处置，不承诺修复上游）。
- Auto 模型语义变更（Auto 仍是故障转移式有序别名组；S3 采用对外模型多别名，不复用 Auto）。

## Stakeholders（干系人）

- **运维管理员**：需要一眼看清「某个候选为何被排除」并据此查状态/探测、查会话、查限流；需要按协议查看错误类型分布。
- **开发者 / 用户**：需要工具（claude code 等）默认模型名开箱可用。
- **平台**：需要渠道健康度不被请求/协议侧错误误伤，保证可用性。

## Architecture（架构总览）

三个支柱，均以**渠道协议**为宿主/挂载点，彼此低耦合：

### 支柱一：渠道协议错误策略（Protocol Error Policy）

- **错误签名**：`status`（必需）+ 可选的 `error.type / code / message` 匹配，命中即归入一个「错误类别」。匹配优先级：精确 status+code > status+type > 仅 status；`message` 匹配为可选且需单测（避免过度匹配）。
- **处置维度**（每类别可配）：是否计入渠道健康错误率、是否 failover、触发动作（none / drain / disable）、下游对客户端的错误码与文案映射。
- **默认策略 = 现状语义（安全态）**：例如 404 仍可转移、400/422 不可转移；「是否计入健康」在默认策略下尽量收敛到「仅上游容量/可用性类错误计入」，请求/协议类不计入——但**默认值的具体调整作为 P1 的评审项**（见 Governance）。
- **协议级错误统计**：按「协议 × 错误类别」计数（含数量与占比），供控制台展示；同时作为 P5 动态感知的数据基础。

### 支柱二：协议特性（Protocol Features）

- **承载与挂载**：在渠道协议上挂载若干「特性」（feature key + 参数）；特性逻辑**在代码中实现并注册**（与「适配器」的区别在于建模与命名：以协议为宿主、可多项挂载、随协议配置启停，而非全局单例）。
- **请求/响应两个扩展点**：请求构造阶段（改写请求体/头）与响应解析阶段（改写/归一响应与 usage）。
- **首批内置特性**：
  - `thinking-roundtrip`：请求侧按上游约定回传 `reasoning_content`（修复 S6，多轮一致）。
  - `tool-schema-normalize`：对齐工具声明（如 `web_search` 的 `input_schema`），修复 S4。
- **与错误策略协同**：特性负责「让本该成功的请求成功」；错误策略负责「确实失败的请求如何被归因与处置」。

### 支柱三：决策轨迹与错误统计可运维性

- **候选轨迹补全**：路由层的排除（尤其是**排空**）也产出候选轨迹项，统一排除原因分类并**显式映射运维动作**（状态/探测、会话、限流、协议、凭据…）。
- **流式失败分类**：日志显式区分「已送达 / 未送达」，并补充响应阶段诊断（是否收到首字节、阶段耗时、上游状态码等），修复 S2/S7。
- **协议级错误面板**：控制台按协议查看各错误类别计数与趋势。

## Phase Breakdown（阶段拆分）

按「先立机制、再落特性、后补观测与别名」排序；每个 Phase 均可独立交付，各自进入「brainstorming → writing-plans」循环。

| Phase | 交付 | 覆盖问题 | 依赖 | 独立可交付 |
|---|---|---|---|---|
| **P1 协议错误策略与错误统计** | 渠道协议错误签名→处置配置；协议级错误计数与展示；健康回喂改由策略决定 | S1（错误不分）/ S4 / S5 / S6（误排空） | 无 | 是 |
| **P2 协议特性挂载 + 首批内置特性** | 渠道协议特性挂载机制；`thinking-roundtrip`；`tool-schema-normalize` | S6 / S4 | P1（同一扩展点与装配） | 是（特性机制） |
| **P3 决策轨迹与流式诊断补全** | 轨迹补「排空」项 + 排除原因分类与运维动作映射；流式失败区分已送达/未送达 + 响应阶段诊断 | S1（可运维性）/ S2 / S7 | 无 | 是 |
| **P4 对外模型多别名** | 外部模型别名列表；解析与缓存失效联动；模型编辑页别名 UI | S3 | 无 | 是 |
| **P5 动态限流感知（延后）** | 基于 P1 沉淀的协议级错误统计，估计渠道+密钥的上游 RPM/TPM 规则 | S1（前瞻） | P1（数据基础） | 是（独立评审门） |

> 顺序提示：P3 风险最低、收益直观，可与 P1 并行；P2 必须在 P1 之后（复用同一协议扩展点与装配）。

## Decisions（关键决策）

| # | decision | choice | rejected alternatives |
|---|---|---|---|
| D1 | 错误处置的扩展点 | **渠道协议**：按协议配置错误签名→处置，并做协议级错误计数 | 全局硬编码四分类；全局单一策略（无法适配多供应商语义差异） |
| D2 | 协议特性形态 | **代码实现特性 + 挂载到渠道协议**（feature key + 参数，可多项启停） | 全局「具名适配器」单例；纯声明式可编辑改写规则（易错难测） |
| D3 | 默认行为 | **默认安全态**：未配置策略/特性时行为与改造前一致；策略/特性逐项启用 | 直接修改默认熔断语义（回归风险） |
| D4 | S3 别名实现 | 在**对外模型上加别名列表**，解析一并命中 | 复用 Auto 单成员（语义偏重）；独立 alias 表（新增实体与失效点） |
| D5 | 排空是否纳入轨迹 | 路由层排除（排空）**也写候选轨迹项**，统一原因分类 | 仅记录网关循环内的跳过（运维看不到排空排除） |
| D6 | 流式失败分类 | 日志显式区分**已送达/未送达**，并补响应阶段诊断 | 维持单一 `connect_failed`（无法定位 S2） |
| D7 | 动态感知时机 | **延后**：先以 P1 沉淀协议级错误统计作为数据基础 | 本期即实现历史学习（无数据基础、过早） |
| D8 | 「已送达」判据 | 沿用 `httptrace.WroteRequest` 结果，扩展阶段诊断字段 | 仅按 `Do` 是否报错（无法区分已送达） |
| D9 | 请求/协议类错误是否 failover | **由协议策略决定**：默认不 failover 且不计入健康；对「换渠道可能可行」的场景由管理员按协议开启转移 | 一刀切全部 failover / 全部不 failover |

## Surface（影响面 shape）

**渠道协议实体与配置**：渠道协议新增「错误策略集合」与「特性集合（含参数）」（JSONB 字段或并列结构，单向迁移新增）；协议校验需覆盖策略/特性合法性（如非法动作、非法正则、未知特性 key）。

**网关上游错误处置路径**：在上游错误处理处按命中协议取策略，据此决定「是否计入健康（回喂状态机的反馈形态）」「是否 failover」「触发动作」「下游状态码/文案」。默认策略保持现状语义。

**协议特性扩展点**：请求构造（改写请求体/头）与响应解析（改写/归一响应与 usage）两处挂载特性逻辑；特性默认关闭，按协议启用。

**健康回喂**：`FeedResult` 的调用由策略驱动（是否喂、喂何种信号），避免请求/协议类错误污染状态机。

**模型解析**：`GetByExternalName` 扩展为「对外名或别名」解析，并联动既有缓存失效钩子（新增别名/改名/删除/启停均需失效）。

**存储与迁移**：渠道协议新增字段（错误策略 / 特性）；外部模型新增别名（字段或结构）。均为单向新增，不改既有列语义。

**控制台 / 前端**：
- 渠道协议编辑页：新增「错误策略」与「特性」配置区。
- 服务状态 / 协议详情：新增「协议级错误统计」（按错误类别）。
- 模型编辑页：新增「别名」输入。
- 调用日志/会话详情：轨迹展示新增「排空」项与排除原因分类。

**决策轨迹数据结构**：候选轨迹项扩展（排空项、排除原因分类、流式已送达/未送达与阶段诊断字段）。

**默认安全态与开关**：错误策略、每个特性均提供全局默认关闭 + 按协议启停；保证未配置时零行为差异。

## Risks & Open Questions

| Risk | Mitigation |
|---|---|
| 错误策略配置错误 → 误判导致全渠道排空或该 failover 不 failover | 默认安全态；配置校验（非法动作/正则拒绝）；服务状态页预演影响；health 语义变更走人工评审门 |
| 协议特性改写破坏上游请求 → 请求失败或计费异常 | 特性默认关闭、按协议启用；表驱动单测（含多轮 reasoning、工具 schema）；计费口径不变 |
