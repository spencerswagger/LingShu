# V2 收敛批次回滚说明（2026-11-16 重写）

> 文件名沿用 `2026-11-15-v2-p1-rollback.md`（既有链接指向这里）；**正文已按收敛后的迁移链
> （`0019_v2_topology` / `0019b_v2_passthrough_credentials` / `0020` / `0022` / `0023*` / `0024`）
> 与渠道域代码摘除（原 #85，已并入 #84）重写**。旧版描述的是已作废的 `0019_v2_facade` 那条线，**照着旧版执行会删掉
> 正在使用的对象**，见 §1。

## 0. 三条硬结论（先读，违反任一都会出事）

1. **回滚 = 代码与数据一起退。** 代码退到批次合入前的 `v2`（下文记作 `R0`，实测用的具体提交
   `e5b579f`），数据退到**批次之前的整库快照**。缺一半都不行：
   - 只还原库、不退代码 → 新代码启动时 `db.Migrate` 会把本批 8 个迁移**再跑一遍**，`0024` 立即把刚恢复的
     10 张表与 3 列再删一次（实测见 §5「反证」），回滚白做；
   - 只退代码、不还原库 → 旧代码启动即撞 `42P01`（`relation "channels" does not exist`）与
     `42703`（`billing_records.channel_key_id` 不存在）并 `exit 1`。
2. **`0024` 删掉的 10 张表 3 列，数据只能靠快照恢复**，不存在「反向 DDL 补回来」的可行做法（见 §2）。
   因此**回滚前必须确认批次前的快照存在且可还原**（§4 步骤 1–2 是备份，不是可选）。
3. **本批保留的对象禁止出现在任何回滚删除清单里**（`magpie_keys`、`external_models.magpie_model` 等，
   清单见 §1）。旧版说明里那两句 `DROP TABLE magpie_keys` / `ALTER TABLE external_models DROP COLUMN magpie_model`
   是**错的**：这两个对象是本批正当保留、转发正在使用的，删了转发立即全挂。

## 1. 禁止删除清单（回滚脚本里出现即视为缺陷）

**转发链路正在使用、本批明确保留：**

| 对象 | 来源迁移 | 用途 | 误删后果 |
|---|---|---|---|
| 表 `magpie_keys`（`token_id`/`key_name` 唯一约束在内） | `0019b` | 令牌 ↔ 代理侧 callerKey（密文）的唯一落点 | 所有 `/v1` 转发鉴权失败（无 callerKey） |
| 列 `external_models.magpie_model` | `0019b` | 对外名 → 代理模型名；准入判据之一 | `/v1/models` 与转发准入全废 |
| 索引 `uq_external_models_magpie_model` | `0019b` | 两对外名不得指向同一代理模型 | 对账按模型聚合会合并 → 误报 |

**本批其他保留对象（同样不许删）：** `internal_models` / `model_links` / `subscriptions`、
`external_models.bound_internal_ref`（`0019`）；`ledger_entries` / `credit_holds`（`0022`）；
`reconcile_windows`（`0023` 新形：`window_start` 主键 + `local_count` / `upstream_count` /
`local_tokens` / `upstream_tokens` / `scroll_offset` 等 11 列）。

**15 张保留表**以代码为唯一来源：`internal/db/v2_tables.go` 的 `RetainedTables()`。
回滚**不需要**动它们任何一张。

## 2. `0024_v2_drop_legacy.sql` 的破坏性清单（回滚前要知道丢了什么）

- **10 张表**：`channels`、`channel_keys`、`channel_models`、`channel_key_events`、
  `channel_model_events`、`channel_tags`、`semantic_tags`、`probe_logs`、`auto_models`、`auto_model_members`
  （`channel_events` 早在 `0009` 删除，不计入本批）。
- **3 列**：`billing_records.channel_key_id`（连带 `idx_billing_key_time`）、
  `sessions.channel_key_id`（NOT NULL，连带 `idx_sessions_key`）、`tokens.tag_id`（引用 `semantic_tags`）。
- 丢的是**历史数据**：渠道/密钥/模型配置、探活记录、标签及其绑定、自动模型组合。
  **本文不给任何 `CREATE TABLE` / `ALTER TABLE ADD COLUMN` 的「反向恢复」SQL** —— 补出来的只是空壳：
  缺数据、缺后续迁移加的列与约束、缺索引，只会让系统看起来能启动、实际读到的全是空值。
  要恢复这些数据，只有一条路：**整库还原到 `0024` 之前的快照**（§4 步骤 3）。

## 3. `applied_migrations` 怎么处理（幂等键 = 完整文件名）

- 迁移框架按**文件名**记账（`applied_migrations.name`），同名文件换内容会被静默跳过、不同文件名同号则都会执行。
- 本批 8 个文件名（唯一来源：`internal/db/V2MigrationFiles()`）：
  ```sql
  -- 诊断：看一眼这个库是哪条链、跑到了哪
  SELECT name FROM applied_migrations
   WHERE name LIKE '0019%' OR name LIKE '002%'
   ORDER BY name;
  -- 见到 0019_v2_facade.sql            → 批次前的「老链」库（本说明要走 §4 还原的就是它）
  -- 见到 0019_v2_topology.sql / 0024_* → 本批的「新链」库
  ```
- **正常回滚（§4）不需要删任何迁移记录**：整库还原后，`applied_migrations` 自然回到批次前的集合。
- 只有「已经按别的方式把 schema 退回去了、却残留新链记录」这种异常才需要清理，语句必须按**实际文件名**命中
  （旧版说明里那句 `DELETE ... '0019_v2_facade.sql'` 在新链库上命中 **0 行**，实测见 §5）：
  ```sql
  DELETE FROM applied_migrations WHERE name IN (
    '0019_v2_topology.sql',
    '0019b_v2_passthrough_credentials.sql',
    '0020_v2_billing_attribution.sql',
    '0022_v2_ledger.sql',
    '0023_v2_reconcile.sql',
    '0023b_v2_reconcile_repair.sql',
    '0023c_v2_reconcile_counts_backfill.sql',
    '0024_v2_drop_legacy.sql'
  );
  ```
  ⚠️ 删记录 = 下次启动重跑这些文件，其中 `0024` 会**再删一遍**表与列。除非你就是要重跑，否则别删。

## 4. 回滚步骤（顺序不许换）

0. **停服**：回滚期间不允许有写入（自动迁移、对账、结算都会动 schema/数据）。
1. **备份现状**（回滚不可逆，先留证据）：
   ```bash
   pg_dump -Fc -Z6 "$DSN" -f current-$(date +%Y%m%d%H%M).dump
   ```
2. **确认批次前快照可用**（不存在就**中止**，别往下走）：
   ```bash
   pg_restore -l pre-batch.dump | head          # 能列内容
   pg_restore -l pre-batch.dump | grep -c magpie_keys   # 应为 ≥1（转发依赖它）
   ```
3. **整库还原到批次前快照**：
   ```bash
   psql "$ADMIN_DSN" -c 'DROP DATABASE IF EXISTS lingshu'   # 或停库后 rename
   psql "$ADMIN_DSN" -c 'CREATE DATABASE lingshu'
   pg_restore --no-owner --no-privileges -d "$DSN" pre-batch.dump
   ```
4. **回退代码到 `R0`**（与还原的 schema 必须成对）：
   - 部署侧：回滚到 `R0` 的镜像/二进制；或
   - 仓库侧：`git revert -m 1 <本批合入 v2 的合并提交>`（一次性退掉迁移 + 后端摘除 + 前端摘除）。
5. **启动自检**（起不来就回到步骤 1 用备份重来）：
   - `curl -s localhost:18080/healthz` → 200；
   - 启动日志无 `42P01` / `42703`，无 `panic`；
   - `SELECT to_regclass('public.magpie_keys'), to_regclass('public.channels')` → 两者都在；
   - 迁移记录条数 = 批次前的条数（本批之后不该多出 8 条）。
6. 业务抽检：管理端登录 / 建令牌 / 建对外模型（含 `magpie_model` 映射）/ 真实转发一条（见 §5 实测口径）。

## 5. 本次实测（2026-11-16，真 PG17 + 真二进制 + 假上游，一次跑完）

- **快照**：用 `R0`（`e5b579f`）的二进制 `-migrate-only` 建出批次前的库 → `pg_dump -Fc` 得 67,479 字节快照。
- **终态库**：同版本新链跑 27 个迁移到 `0024`；
  - 10 张退役表：`(全部已删)`；
  - 3 列：`0` 残留；
  - `magpie_keys` 与 `external_models.magpie_model`：**仍在**（`magpie_keys|1`）。
- **迁移记录命中**：本节 §3 那份 `IN (8 个文件名)` → 命中 **8 行**；`name = '0019_v2_facade.sql'` → 命中 **0 行**
  （证明旧说明那句话在新链库上是空操作）。
- **执行回滚**（§4 步骤 3 + 4）：还原快照 + 起 `R0` 二进制 → `channels` 回来、`billing_records.channel_key_id` 回来、
  `magpie_keys` 在、`0024` 记录 **0**。
- **系统可用性**：`/healthz` 200；登录 + 改密 + 建令牌 + 建对外模型（`MagpieModel=upstream/gpt-4o`）全 200；
  真实转发 `/v1/chat/completions` → **200**，上游收到 `{"model":"upstream/gpt-4o",...}`（model 改写生效），
  下游拿到的响应体与上游一致；callerKey（`magpie_keys`）插入后即可用；
  启动日志 `panic=0`、`42P01`/`42703` 各 0 次，唯一 ERROR 是价格源指向 `127.0.0.1:1`（测试环境故意指空，与本批无关）。
- **反证（只还原库、不退代码）**：让**新链**迁移器连「已还原的老库」→ 8 个迁移"全部成功"重跑，
  10 张表与 `channel_key_id` **再次消失**、`0024` 记录变 1。这就是 §0 结论 1 的实测依据。
- **口径提醒**：`R0` 版本的转发路径**尚未装配计费钩子**（`OnComplete` 刻意不注入，属第③件事），
  所以回滚后转发不落 `billing_records` / `call_logs` 是**该版本既有行为**，不是回滚造成的损坏；
  回滚前后行为一致即是正确性判据。

## 6. 回滚**不需要**关心的东西

- 计费口径与价目：`billing_records` 的金额、三段 token、`external_models.sale_rates`、`billing.*` 系统配置未因本批改变。
- 身份与资金：`users` / `tokens`（除 `tag_id` 列）/ `credit_wallets` / `credit_flows` / `audit_logs` 结构未变（列删除见 §2）。
- 保留表的**数据**：本批只删退役表，15 张保留表的数据一行未删（`F7` 判据：迁移前后行数不减）。
- 前端：与后端同批下发，随代码回退一起退，无独立数据迁移。
